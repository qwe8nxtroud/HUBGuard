Ноду сканируют постоянно: перебирают порты, щупают пути, долбятся в 443 сотнями
соединений в секунду. Это греет процессор, засоряет логи и иногда роняет ядро.

HUBGuard считает новые соединения средствами ядра и банит источник на время.
Логи не парсит: у Xray, sing-box и 3x-ui форматы разные, а счётчики conntrack
одинаковые — поэтому работает с любым ядром и не ломается при его обновлении.

```bash
sudo ./hubguard.sh              # меню
sudo ./hubguard.sh plan         # что будет сделано, ничего не меняя
sudo ./hubguard.sh apply        # включить
sudo ./hubguard.sh top          # кто сейчас в бане
sudo ./hubguard.sh rollback     # снять всё одной командой
```

> HUBGuard вырос из практики **[vpn-hub.pro](https://vpn-hub.pro)** — там разборы
> по Remnawave и Xray, диагностика нод и то, из-за чего всё это ломается на живых
> серверах.

## Почему он не банит своих

Это главное. Похожие скрипты блокируют **подсетями** из готовых списков: один
сканер в `/16` провайдера — и без доступа остаётся весь дом вместе с вашими
платящими клиентами. Молча, без ответа, до тех пор пока кто-то не заметит.

HUBGuard построен от обратного.

**Белый список проверяется первым.** Не после бана, не «в следующей версии», а
первым правилом цепочки. В нём сразу: loopback, приватные сети и **CGNAT
`100.64.0.0/10`** — за ним сидят мобильные операторы, и одна ошибка там отрезала
бы разом много клиентов.

**Автобан кладёт только одиночный адрес.** Подсеть автобаном не блокируется
никогда — это проверяется тестом, а не обещанием в README.

**У бана всегда есть срок.** По умолчанию час. Ошиблись — рассосётся само.

**Отказ вместо самострела.** Если правила отрежут текущую SSH-сессию, скрипт
не применяет ничего и говорит почему. Адрес сессии добавляется в белый список
до применения правил, а не после.

**Своя таблица nftables.** Чужие правила не трогаются, откат — удаление одной
таблицы без побочных эффектов.

## Как это работает

```
новое соединение на 443
        │
        ├─ established/related ────────────────► пропустить
        ├─ адрес в белом списке ───────────────► пропустить
        ├─ адрес в бане ───────────────────────► drop
        └─ больше 60 новых за минуту ──────────► в бан на час, drop
```

Всё живёт в отдельной таблице `inet hubguard`. Порог, окно, срок бана и порты
настраиваются флагами.

Опционально подключаются внешние списки адресов — но **каждый адрес из списка
проходит через белый список**, прежде чем попасть в блокировку. Чужой фид не
может заблокировать вашего клиента. По умолчанию списки выключены: включаются
явным флагом `--feed <url>`.

## Установка

Нужен `nftables` — он есть в Debian 11+, Ubuntu 20.04+ из коробки.

```bash
git clone https://github.com/qwe8nxtroud/HUBGuard.git
cd HUBGuard
sudo ./hubguard.sh plan     # посмотреть, что будет
sudo ./hubguard.sh apply
```

Сначала `plan` — он ничего не меняет и показывает пороги, белый список и ваш
адрес. Потом `apply`.

## Команды

| Команда | Что делает |
|---|---|
| `status` | активна ли защита, сколько адресов в бане |
| `plan` | что будет применено, без изменений |
| `apply` | включить защиту |
| `top` | кто в бане |
| `watch` | живой просмотр |
| `ban <ip>` | забанить вручную |
| `unban <ip>` | снять бан |
| `allow <ip\|cidr>` | добавить в белый список |
| `feed-update` | перечитать внешние списки |
| `rollback` | снять правила |
| `uninstall` | удалить всё |

Флаги: `--ports "443 8443"`, `--rate 60`, `--window minute`, `--bantime 1h`,
`--feed <url>`, `--dry-run`, `--yes`.

Белый список ведётся руками в `/etc/hubguard/allow.list` — по адресу или подсети
в строке, комментарии через `#`.

## Настройка порога

По умолчанию 60 новых соединений в минуту с одного адреса. Живой клиент открывает
единицы, сканер — сотни, так что запас большой в обе стороны.

Если у вас за одним адресом сидит офис или большой CGNAT, поднимите порог или
добавьте адрес в белый список:

```bash
sudo ./hubguard.sh --rate 200 apply
sudo ./hubguard.sh allow 203.0.113.0/24
```

## Проверено

44 теста идут на каждом коммите, **без root и без nftables** — вся логика вынесена
в чистые функции. Проверяется в том числе то, ради чего скрипт написан:

- адрес из белого списка не попадает в бан;
- автобан отказывается принимать подсеть;
- при риске отрезать SSH-сессию `apply` не делает ничего;
- `plan` не создаёт файлов и не меняет правил;
- правило белого списка стоит выше правила блокировки.

Плюс `shellcheck -x` без единого замечания.
